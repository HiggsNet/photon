# Gossip 优化讨论草案

以 Windows 分支 `e7073ea2` 为讨论基线。先讨论协议，再讨论 daemon、状态和日志。

## 值得保留的边界

- Bootstrap 提供地址，签名、父级委派和撤销决定信任。收到对象不等于生效，验证并提交后才发布可信版本。
- 摘要一致就结束；有差异才查目录、拉 Zone。通知负责加速，漏掉通知仍能靠周期同步收敛。
- 隧道消费已提交的可信事实，不等待 Gossip 写盘或一轮同步结束。入网授权、Gossip 同步、隧道就绪分别表达。

## 第一轮：两条协议旁路

**按键和版本拉单条记录。** 最早的 UDP `fetch_record` 用于补齐前驱：先收到 v3、缺 v2，就请求 v2（`200ce175`）。`58702f17` 改为以最新合法签名状态为准，删除了等待和补前驱的流程。随后引入的 TCP object pull 同时支持 Zone 和单条 record（`67b66261`），但清理前的主动同步已经只请求 Zone。

已移除单条 record 拉取的线上接口。Zone 快照继续携带记录、签名和版本。当前目录的差异粒度是 Zone，变化也可能来自委派或撤销。若以后遇到“大 Zone、小更新”的流量问题，再设计可验证的差量和全量回退。

**摘要捎带目录第一页。** `FirstPage` 原是 `CatalogSummary` 的可选字段，在分页同步引入时就默认不发送（`dc8ee4b4`）。捎带首页在摘要不一致时可省一次目录请求和响应。

已移除 `FirstPage`、摘要内的 `NextCursor` 和相应的接收处理。摘要只携带根摘要和 Zone 数量。摘要不一致时，用空 `cursor` 的 `FetchCatalogPage` 请求目录第一页，再用目录页返回的游标请求后续页。

## 公共 Gossip 传输：保留现有设计

当前设计合理，继续用 UDP 交换摘要、目录和变更提示，用短连接 TCP 拉取完整 Zone。当 TCP 拉取不可达而已观察到的 UDP 路径仍可用时，保留 UDP 分块回退。这样空轮无需建连，NAT 映射有效期间也可以通知出站节点。

最初使用 UDP 是为了避免为每个邻居维持连接。2026-06-02 的 `67b66261` 为避免在公网依赖 IP 分片，把默认 UDP 报文预算从 64 KiB 降到 1200 字节，并引入短连接 TCP 拉取超预算对象。设计保留 UDP 小包交换，只有发现需要拉取对象才建立 TCP 连接。

引入 UDP 分块的提交（`e1b8d967`，2026-06-04）记录了家庭 NAT、CGNAT 和无端口映射的场景。内网 A 主动向公网 B 发 UDP 后，B 可以沿已观察到的 UDP 路径联系 A。当 B 要拉取 A 的 Zone 时，旧协议要求 B 另开 TCP 连接拨入 A。UDP 分块让 B 可以沿现有路径拿到完整快照。参见[当时的公网测试文档](../refer/public-internet-test.md#6-nat--cgnat-节点)。

可靠传输和连接寿命是两个独立的选择。TCP 或 QUIC 可以按同步轮次建立连接，双方在同一条连接交换摘要、请求目录和拉取对象，完成后关闭。保留少量长连接也是一个选项，适用于需要在两轮同步之间立即发通知的邻居。

双向同步是公共协议的能力。若 A 只能出站而 B 可以监听，A 发起连接后，B 可以在同一条连接上请求 A 的 Zone，无需另拨 A。连接关闭后，B 要等 A 再次连入才有这条路径。

需要单独比较两轮之间的通知。现有 UDP 可以让 B 沿观察到的地址通知 A，前提是 NAT 映射仍有效、过滤规则允许返回流量。A 的出站包可刷新映射，B 缓存的地址本身无法延长映射寿命。纯 TCP 短连接在两轮之间没有这条通知路径。若要保留低延迟通知，可以让 A 维护少量出站长连接，也可以保留 UDP 提示，让 A 收到提示后主动发起一轮双向可靠同步。两种方式都需要周期同步兜底，以应对断线或提示丢失。

按轮建连是评估可靠传输的基线。连接层负责拨号、接收、超时和关闭，同步层负责摘要、目录、Zone 拉取和验证。断线结束本轮，下一轮从已提交的状态重新对比。按轮建连会增加空轮的握手成本。若不保留独立通知路径，轮次之间的变更也要等到下一次连接才能传递。评估时应把撤销等变更的传播延迟和空轮成本放在一起看，再决定是否为少量邻居保留长连接。迁移涉及双方的传输和消息交换，属于独立的协议改动。

不同邻居的连接可以并行收发，各自持有本轮的摘要、游标和待拉取对象。连接可以读取已提交的快照，收到对象或发生超时就把结果交回公共事件循环。事件循环独自更新共享的 Gossip 状态，并通过现有 Store 按最新已提交的状态验证、合并和发布。网络读写期间不持有 Store 的写锁。如果目录与对象之间的摘要对不上，刷新目录再比较。单个邻居同时双向拨号造成的重复会话，由连接层合并或择一。

出站调度按邻居分配并发名额，每个邻居最多一轮进行中，全局限制并发数。拨号、读写和整轮都有截止时间。某个邻居超时，只结束它这一轮、释放名额，并对它单独退避。所有名额都忙时，其他邻居等空位。单条 TCP 连接内，排在大对象后面的消息可能被拖延。

现有 TCP 拉取已经采用并行 I/O、串行处理结果的方式。将来如果重新评估迁移，需要比较能删掉的分块、补传和缓存，以及新增的连接去重、超时和调度，同时验证网络可达性和撤销传播延迟。

迁移前需要确定要覆盖哪些网络。如果原问题只是 B 无法反向拨入 A，A 发起的双向 TCP 会话就能覆盖该场景。如果 A 到 B 的出站 TCP 也受限，才需要考虑 QUIC 等可用传输。QUIC 提供运行在 UDP 上的可靠流，仍需验证目标网络能否建立 QUIC 连接。采用可靠流后，Gossip 可以把报文分段和丢包重传交给传输层，继续负责摘要比对、对象验证和同步重试。

## Linux Daemon 入口收敛

Linux 统一使用 `photon daemon` 运行 Gossip。已删除 `advanced sync serve` 和 `advanced sync once` 的 CLI 入口、独立启动流程和事件循环。它们原先和 daemon 共用 GossipDriver 和协议状态机，但各自启动 UDP、TCP 对象服务和拉取 worker，并消费同样的输入、完成和续处理事件。

`advanced sync status` 仍可查询在线 daemon 或离线 checkpoint。内部 `sync_trigger` 仍只确认已调度。如果以后需要立即同步并等待结果，应在在线 daemon 中按指定 peer 的会话结果区分成功、失败和超时。

- `phase2-run-smoke` 覆盖双节点记录双向同步、Zone 签名校验及重启后收敛。
- 三节点中间节点重启、bootstrap 授权和在线撤销传播均使用 daemon，直接等待记录、授权和发现结果。
- `nat-daemon-observed-smoke` 合并两套 observed path 场景，覆盖记录传播与重启后从新入站包重新学习 observed UDP 地址。

## Gossip Checkpoint

删除 observed 路径的上次同步和失败计数。同步结果属于对端会话，无法据此判断本轮走了哪条地址。观察地址、有效期、换址宽限和活动时间只留内存。重启后等待对端发来经过验证的包重新学习地址。纯续期不再触发持久化，原有 5 秒续期合批随之删除。

发现地址只在首次选定、发生变化或失效清除时更新 checkpoint。同一地址在后续扫描中继续作为候选，删除只用于展示的发现时间戳。重启后遇到暂时不可达的对端，由现有的发现和重试流程处理。退避、relay 去重和拒绝缓存继续使用现有 checkpoint。

Linux 隧道生命周期用内存中的活动时间判断何时暂停重建。达到阈值时保存暂停标记，IPsec 规划和状态展示读取这个标记。Gossip 发现和地址过期仍独立运行。重启后尚未暂停的 peer 从新的观察窗口开始，已暂停的 peer 等到新的认证活动后解除暂停。

签名撤销立即使节点或子树失去授权并清理运行态。撤销 Zone 正文和 Gossip checkpoint 由显式的 `advanced recovery purge-revoked --apply` 删除，父区中的签名撤销证明继续保留。
