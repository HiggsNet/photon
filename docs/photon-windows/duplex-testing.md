# Windows Mesh TCP 收发调度实测

2026-11-03，Windows Test 和 More 通过内网地址建立 ESP 隧道。对照基于
`1021774b`，临时采样构建分别运行单流和四流 TCP 下载、上传，每项发送约 6 秒。
吞吐按接收字节及包含收尾的实际时间计算；丢包计数覆盖每个构建的四项测试。

| 调度 | 单流下载 / 上传（Mbps） | 四流下载 / 上传（Mbps） | 出站队列拒收 | 出站平均排队 |
| --- | ---: | ---: | ---: | ---: |
| 当前主循环 | 466 / 343 | 614 / 408 | 85,487 | 0.61 ms |
| 出站积压且 ESP 队列未接近满时，同轮多处理一包 | 475 / 362 | 660 / 409 | 80,889 | 0.61 ms |
| 出站队列容量 64 → 256 | 462 / 411 | 605 / 413 | 23,092 | 1.15 ms |

基线的出站拒收中，84,149 个是测试连接的无负载 TCP ACK，1,332 个是含
TCP 负载的包。约 71% 的拒收发生时主循环处于出站分支，约 21% 处于
ESP 入站分支。这是拒收时采到的分支，不能单独证明某一个分支造成了拒收。
出站处理平均 19.3 µs，其中 AES 约 0.6 µs，UDP 写入约 7.5 µs。
增加出站批次后，ESP 平均排队从 43 µs 升到 85 µs。容量与批次实验均为
临时构建，Windows Test 恢复到 `1021774b`。

下一轮用同一个内网端点对照单向 TCP 和同时收发的 TCP。当前已经有独立的
出站和入站队列，但一个主循环串行消费两者。并行原型需要分别保持每个方向的
顺序和状态所有权，并在真正写入前核对仍有效的隧道、CHILD 和授权。
控制面更新、换钥、撤销和设备关闭要有明确的同步边界，避免旧队列项越过它。
下载 ACK 仍属于出站路径，验收同时看两向吞吐、排队、拒收和 TCP 重传。

## 入站 ESP 解密并行试验

原型把入站 ESP 解密移到单独的 FIFO 工作协程，任务和结果各有一个 64 包的
队列。主循环仍选择入站 SA，消费完成项后重新检查授权并写入 Wintun；出站仍
由主循环负责。临时原型的竞态测试验证了真实 ESP 完成项的 FIFO 顺序，以及
代次重置后拒绝已解密的旧完成项。现有授权撤销回归也通过。

同一 Windows Test 和 More，每轮发送 8 秒。双向时每个方向两条 TCP 流，
用同一轮含收尾的实际耗时计算两个方向的吞吐。

| 模式 | 下载（Mbps） | 上传（Mbps） |
| --- | ---: | ---: |
| 裸内网双向 | 799 | 903 |
| 基线单向（各一轮） | 480 | 384 |
| 基线双向第一轮 | 555 | 8.2 |
| 基线双向第二轮 | 178 | 3.5 |
| 解密并行单向（各一轮） | 368 | 399 |
| 解密并行双向第一轮 | 394 | 12.9 |
| 解密并行双向第二轮 | 403 | 15.6 |

四轮合计，出站队列拒收由 77,126 降到 3,544，但入站拒收由 1,780 升到
62,473。原型的入站数字合计了 UDP 分流和解密任务队列，不能进一步拆分。
单向下载下降，双向上传仍只有十几 Mbps。原型未纳入生产代码，Windows Test
已恢复运行 `1021774b`。

基线出站样本从 AES 完成到开始交付的复核阶段平均 1.17 µs，包含隧道、SA
和授权检查。把解密移到工作协程后，包仍要回主循环复核和交付。后续原型需要
验证完整的收发交付分离，并单独追踪下载 ACK 与上传数据在发包队列中的竞争。

## 双向上传受压与队列对照

同一 More 内网端点，每方向两条 TCP 流，各轮发送 8 秒。默认调度复测时，
单独上传 337 Mbps，同时下载约 584–594 Mbps 时，上传仅 11–16 Mbps。

| 下载限速对照（只限制 More 的测试发送器） | 实际下载（Mbps） | 同时上传（Mbps） |
| --- | ---: | ---: |
| 50 Mbps | 50 | 313 |
| 150 Mbps | 145 | 248 |
| 300 Mbps | 299 | 132 |

下载压力与上传下降可以稳定关联，具体是上传数据丢失、返回 ACK 丢失还是
调度延迟，各自贡献尚未分开。基线四轮出站队列拒收 106,076 个，其中 104,863
个是测试 TCP 的无负载 ACK、1,209 个带负载。此统计包含单向和双向轮次，
不能当作双向上传的单独丢包率。

| 临时方案 | 单独上传（Mbps） | 双向下载两轮（Mbps） | 双向上传两轮（Mbps） |
| --- | ---: | ---: | ---: |
| 默认调度 | 337 | 584 / 594 | 15.5 / 10.9 |
| 八个固定 8 包流桶 | 70 | 627 / 596 | 16.2 / 19.2 |
| 出站积压时把 ESP 批次缩到 2 | 365 | 536 / 507 | 11.2 / 15.9 |
| 共享 64 包容量，按流轮询，满时从最深桶让位 | 372 | 525 / 588 | 26.8 / 15.4 |

缩短 ESP 批次使四轮入站拒收由 534 升至 34,577。共享容量保住了单向速度，
双向上传仍然不稳定。三个临时方案均未启用。独立收发路径仍需覆盖交付；
应用上传的数据与下载 ACK 共用出站，而应用下载的数据与上传 ACK 共用入站，
所以仅把 ESP 解密移走或仅按流拆出站队列都不足以完成双向验收。

## 上传 TCP 序号对齐

More 内网两条下载流加一条被追踪的上传流，发送 8 秒。Windows 在读取
Wintun、出站队列拒收、UDP 写入成功、入站 ESP 解密成功和 Wintun 写入
成功处记录测试流 TCP 头；More 在隧道内侧抓同一流，不保存应用负载。
按 TCP 字节区间比较，避免 More 合并报文导致包数不可比。

- 基线下载 566 Mbps、上传 7.1 Mbps。Wintun 已读到 5,867 次带负载的
  发送，Photon 出站队列拒收了其中 199 次，共覆盖 37 段唯一字节区间。
  该流未观测到 Wintun 读取队列拒收。
- 最长一次 ACK 进度停顿约 2.12 秒。停顿起点缺失的字节所在数据包有三次
  被 Photon 出站队列拒收。More 端 ACK 进度同样停顿约 2.12 秒，说明
  Windows 等待期间 More 没有推进累计确认。重传后 More 收齐全部字节。
- More 发出的 1,152 个唯一 ACK 值中，1,144 个在 Windows 解密后出现，
  这 1,144 个都交给了 Wintun。该样本确有返回 ACK 缺失，但主要长停顿
  已经出现在 More 发出 ACK 之前。
- 已启动的 256 包队列诊断得到下载 554 Mbps、上传 19 Mbps，出站拒收
  86 次，最长 ACK 进度停顿仍约 0.93 秒。容量对照未进入产品。

9 µs 是从出站主循环取包到 AES 开始的前置段，包含地址解析、选路、当前
隧道和策略准备及检查。临时构建测得该段约 9.6 µs，AES 约 0.4 µs，
加密后到交付前的复核约 1.1 µs。该序号样本将反复丢失的位置定位到
Photon 在 Wintun 读取之后、ESP 加密之前的队列，不能由 Windows 裸网卡
吞吐或 ESP 加密速度解释。取样只覆盖一条上传流，不能外推为全部丢包构成。

## UDP 直接提交和独立发送协程

固定 More 内网端点，每轮发送 8 秒。双向每方向两条 TCP 流。三个版本都
保留 64 包的 Wintun 出站队列；独立发送使用无缓冲交接，只有正在写的包。

| 方案 | 单流下载 / 上传（Mbps） | 双向下载两轮（Mbps） | 双向上传两轮（Mbps） | 出站队列拒收 |
| --- | ---: | ---: | ---: | ---: |
| 原 Go UDP 路径 | 485 / 367 | 543 / 566 | 14.1 / 15.6 | 84,581 |
| 直接调用 Winsock | 452 / 379 | 582 / 592 | 10.6 / 7.6 | 114,840 |
| 独立 UDP 发送协程 | 481 / 305 | 535 / 581 | 16.8 / 9.1 | 121,909 |

直接调用版本的 1,007,104 次提交中只有一次返回 IO_PENDING；平均写入
7.73 → 8.01 µs。改用直接调用未缩短这一段。独立协程版本仍由主循环选路和
加密，再复制密文交接，单协程按顺序写入。发送时校验隧道代次、授权版本和
截止时间。累计成功 905,340 次，过期或失效丢弃 235 次，写失败 0 次。
原型的过期与失效测试以及现有 ESP 顺序和授权回归通过。

独立发送双向时使用约 1.65–1.67 个逻辑核，基线约 1.33–1.36 个。
从主循环取包到交付完成的平均计时由 19.4 增至 34.2 µs，该计时包含跨协程
交接，不能当作主循环独占 CPU 时间。两种实验均未启用。

## 发送通道直接消费原队列与真实 ESP 合并提交

临时 Windows 构建固定 More 内网端点。每轮发送 8 秒，双向时每方向两条 TCP
流。保留原 64 包出站队列。发送通道原型直接消费此队列，以只读路由和授权
快照完成选路、ESP 封装、UDP 写入，普通接收仍由原所有者处理到 Wintun。
控制事件会先撤回快照，等在途提交越过边界，再发布新快照。Babel ESP
仍在暂停业务发送的控制窗口内顺序写入。

| 方案 | 单向下载 / 上传（Mbps） | 双向下载（Mbps） | 双向上传（Mbps） |
| --- | ---: | ---: | ---: |
| 端点复用及 Wintun 读锁解耦基线 | 470 / 386 | 611 / 309 | 5.5 / 6.9 |
| 独立发送通道 | 506 / 287 | 583 / 577 | 14.5 / 28.3 |
| 主循环等长 ESP 合并提交（最多 4 包） | 466 / 413 | 555 / 482 | 26.7 / 4.7 |

独立发送原型四轮合计出站队列拒收 71,135 → 9,476，采样平均等待
478 → 161 µs，取包至交付完成 18.8 → 15.4 µs。针对旧快照撤销、
ESP 顺序和源授权的竞态回归通过。单向上传退步，双向仍离单向能力很远。

合并提交原型只处理已就绪的包，按同端点、同 CHILD、同完整密文长度聚合，
每个成员独立封装和复核。1,124,867 个 ESP 报文使用 415,286 次写入，
报告写错误为零。实验用共享 socket 写锁保护临时分段选项及复原，
尚未验证可上线的逐消息实现。合并版四轮出站拒收降至 19,033，入站拒收
由 1,740 升至 5,878，双向结果波动大。

独立发送的额外序号诊断轮有一条下载流超时，吞吐结果不纳入上表。
在可对齐的上传流上，记录到出站队列拒收 86 次、Wintun 原始读队列拒收
9 次。More 发出 331 个不同累计 ACK 值，Windows 解密看到其中 327 个，
Wintun 也收到同样的 327 个。More 的 ACK 进度最长停约 7.2 秒，
说明该轮仍存在数据未及时抵达导致的反馈停顿，不能仅凭总体队列拒收下降
判定每条 TCP 流已经稳定。

### 同一 ACK 值的逐次对齐

对上面的超时轮按连接内时间重对齐。某个上传数据段在 Windows 的 UDP
写入成功时间约为连接开始后 4.139、4.446、5.056、6.258、8.661、
13.473 秒。More 隧道内侧只看到该段两次，约为 6.262 和 13.474 秒。
这将第一次送达前的多次缺失定位在 Windows UDP 写入成功之后、
More 内侧收到数据之前，尚未用外层 ESP 抓包区分链路和 More 接收路径。

More 第一次收到该段即发出推进累计确认的 ACK。Windows 约在 6.261 秒
记录到该 ACK 解密成功，但没有对应的 Wintun 写入成功记录。同一 ACK
值在 13.475 秒再次出现并交付。因此上一节按不同 ACK 值统计的 327/327
不能证明每一次 ACK 都交付；这一次同时涉及上传数据未达和已解密 ACK
未交付。接收前置复核、驱动写失败和外层报文缺失需要单独取证。

### More 网卡与隧道内侧对齐

重新运行独立发送原型，两条下载流约 560 Mbps，一条上传流约 7.1 Mbps。
More 的网卡抓到 400,000 个外层报文后停止，内核报告抓包丢失为零。按实际
覆盖的同一 SPI 序号区间比较，Windows 报告 UDP 写成功的 4,330 个测试报文
全部在 More 网卡出现，另外 1,326 个位于抓包范围外，未计入丢失。

约 0.92 秒的上传停顿中，缺失字节的前四次发送 ESP 序号为 14696、
26527、37615、59196。四次均到达 More 网卡，前三次落后该时刻观测到的
最高序号 46、42、48 位。第四次按序到达后才在 More 隧道内侧出现。
按网卡抓包时间排序，相关 SPI 的 153,943 个包中，14,792 个落后至少
32 位、5,472 个落后至少 64 位，最大 377 位。对齐到测试上传数据，按序
到达的 3,478 次发送都在 20 ms 内出现在内侧；落后 32–63 位的
130 次中仅 77 次匹配。此窗口是观测相关性，不等于逐包内核丢弃原因。

该轮 1,156 个解密后的测试 ACK/控制包全部交付 Wintun，与前一轮的单次
未交付不同。另一次复现约 593/11.6 Mbps 时，More 宿主机 UDP 接收错误
与缓冲丢失计数没有增加。More 实际入站 SA 的防重放窗口和丢弃计数需要
单独核对；宿主机不存在 `/proc/net/xfrm_stat`，不能据此排除防重放。

按网卡抓包时间对齐，三个未到达内侧的发送落后 46、42、48 位。
随后只读查询 More 的实际内核 SA，匹配抓包 SPI `0xc472f68e`，确认配置
窗口为 32，累计超窗口丢弃 37,893，重复重放与完整性失败计数均为 0。
累计值不等同于 400,000 帧抓包窗口内的增量。另一轮 Windows 测试 SA
同样配置 32，累计超窗口丢弃 45,258。证据确认了 More 接收端防重放
丢弃，尚未定位外层 ESP 在 Windows、虚拟交换路径或 More 网卡接收路径
中的重排起点。未更改 More 的 SA 或防重放配置。

### Windows VirtIO 出口与 More 网卡入口

保持 More 入站防重放窗口 32，复用独立发送诊断版。Windows PktMon 仅在
VirtIO 网卡组件采集指定 UDP 端口，More 同时在物理方向的网卡入口采集。
两条下载流合计 546 Mbps，单条上传流 6.3 Mbps。Windows 采集报告没有
事件丢失。按同一 SPI、两端都捕获到的 215,120 个 ESP 序号比较：

| 观测点 | 落后更早到达的最高 ESP 序号至少 32 位 | 最大落后 |
| --- | ---: | ---: |
| Windows VirtIO 组件 | 0 | 0 |
| More 网卡入口 | 29,096 | 1,037 |

计数采用严格早于本包的捕获时间，忽略同时间戳的先后关系。被应用层
明确标记为上传流且两端均可见的 4,477 个报文中，259 个在 More 出现了
超 32 位的落后。窗口未调整。此结果把乱序范围缩到 Windows VirtIO
观测点之后、More 网卡观测点之前；该 Windows 观测点不能代替宿主 tap
或物理链路的实际出站顺序。

第二轮在 VM 101 所在 Proxmox 增加 `tap101i0` 和
`enp2s0f0np0` 两个软件抓包点。两条下载流合计 565 Mbps，单条上传
11.5 Mbps。四个观测点共同覆盖同一 SPI 的 229,356 个序号：

| 观测点 | 落后至少 32 位 | 最大落后 |
| --- | ---: | ---: |
| Windows VirtIO 组件 | 0 | 0 |
| Proxmox tap101i0 | 0 | 0 |
| Proxmox enp2s0f0np0 软件发送点 | 0 | 0 |
| More ens16 接收点 | 29,706 | 798 |

Proxmox tap、物理网卡软件发送点和 More 三点的全部 298,196 个序号集合
相同；按这个更大的共同集合，前两点仍完全有序，More 有 41,355 个序号
落后至少 32 位。4 点共同范围内 7,240 个已标记的上传流报文有 354 个
在 More 落后至少 32 位。取样证明该轮在 Proxmox 软件发送点之前未观察到
乱序。这个点位于物理发送之前，尚不能区分发送 NIC、交换链路和 More
所在宿主及虚拟 NIC 的接收处理。未调整窗口、队列或网卡参数，Windows
测试结束恢复 `1021774b`，PktMon 停止并撤回临时筛选器。

### Wyse 物理入口、More tap 和 guest 接收点

只读确认 More 是 Wyse（10.16.255.201）的 VM 302，网卡 MAC
`96:6d:a6:e8:c4:a8`。Wyse 从 Realtek `enp1s0` 收包，经
`vmbr0` 和 `tap302i0` 交给 guest 的 `ens16`。发送宿主的软件物理
出口也同时抓取同一 UDP 流。两条下载流合计 514 Mbps，单条上传 6.1 Mbps。
按严格早于本包的捕获时间排序，四点共同覆盖同一 SPI 的 282,366 个序号：

| 观测点 | 落后至少 32 位 | 最大落后 |
| --- | ---: | ---: |
| Windows 所在宿主的物理网卡软件发送点 | 0 | 0 |
| Wyse `enp1s0` 软件接收点 | 0 | 0 |
| Wyse `tap302i0` 交付点 | 0 | 0 |
| More `ens16` 软件接收点 | 47,366 | 1,540 |

应用标记的 4,917 个上传报文均在四点出现，其中 285 个首次在 More
达到超 32 位的落后。乱序首次可见于 tap 和 guest 观测点之间，尚不能
区分 vhost/VirtIO、guest 接收队列或 guest 接收合并。Wyse 物理口是
r8169，只有 rx-0 且 RPS 为 0。VM 302 启用 vhost、packed VirtIO 和
4 对队列；guest 的四条接收中断各在不同 vCPU，RPS 均为 0。
观察期间没有修改队列、网卡特性或防重放窗口，Windows Test 恢复原版。

### More VirtIO 四队列与单队列对照

Windows Test 固定使用 More 内网端点 `10.16.255.11:33570`，每组同时
运行两条下载 TCP 流和一条上传 TCP 流，约 8 秒。两组使用同一诊断版，

### 1.2 Gbps UDP 的供包节奏与主循环等待

沿用上述 VF6、Less、单 SA 和逐包发送路径。临时构建用 QPC
测量每 128 个应用序号中的一个从入队到出队的时间，并记录超过
100 µs 的非上传主循环分支。Windows 发送器用 QPC 统计每 100 µs
内成功返回的应用写调用。第一轮仍每 16 包校准节奏并使用睡眠，
第二轮逐包忙等目标时刻，实际供包均约 1200 Mbps，各 230,769 包。
